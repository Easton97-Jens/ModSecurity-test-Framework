## Motivation and problem statement

The user explicitly selected one workflow updater when the canonical
common-version maintenance path and the pinned workflow-tool updater overlap.
The standalone updater had protections that must not disappear during that
consolidation: candidate/base identity binding, asset checksum verification,
isolated proposed-tree contracts, and exact Draft PR state controls.

## Affected components and security boundaries

- `.github/workflows/check-common-versions.yml`: the sole trusted maintenance
  orchestrator. It continues to run only from schedule/manual trusted-default
  execution and retains its repository-limited publisher App token.
- `ci/tools/update-workflow-tools.py`: remains the narrow lock/pin helper; it
  now snapshots the pre-plan input surface and validates the native candidate
  generated by the canonical plan rather than owning a second publisher.
- `ci/checks/security/check-ci-security-contract.py` and direct tests: bind
  the new snapshot, candidate digest, asset, proposed-tree, Draft PR, token,
  trigger, and branch-scope controls exactly.

Parent source and gitlink are unchanged. MRTS remains read-only and unchanged.

## Acceptance criteria

1. `check-common-versions.yml` is the only workflow publisher for canonical
   Action/tool maintenance; `.github/workflows/update-workflow-tools.yml` is
   removed.
2. Candidate and publisher snapshot the fixed updater inputs before applying
   the caller-bound plan, then independently derive the native candidate.
3. Both derivations retain release provenance, changed-tool checksum, and
   isolated proposed-tree validation. The publisher must match the candidate
   job SHA-256.
4. The publisher remains trusted-default-only, uses the same narrowly scoped
   App token, and reuses only one exact Draft PR with an allowlisted branch
   diff whose native workflow-tool subset equals the base-derived output. No PR
   trigger, force push, merge, permission expansion, or token expansion is
   introduced.
5. The native helper and unified workflow regression/negative contract tests,
   action-pin, workflow, canonical-view, CI-security, documentation, and
   Change Record checks pass.

## Alternatives considered

Keeping two publishers was rejected because it duplicates the same pinned
Action/tool maintenance surface. Removing the helper or weakening its checks
was rejected because that would lose independently useful supply-chain and
publisher-boundary controls.

## Implementation decision

The canonical common-version workflow is the single publisher, while the
native helper remains the independently testable lock/pin candidate validator.

## Changed files and tests

- Removed the standalone workflow and its active generated-path/allowlist
  entries.
- Added bounded `RUNNER_TEMP` snapshot directories and canonical-generated
  candidate validation to the native helper.
- Added the snapshot and validation steps to both canonical candidate and
  publisher jobs, with a cross-job candidate SHA-256 check.
- Added a reviewed `github-script` check for the fixed branch, title, marker,
  Draft state, default base, ancestry, and exact generated-path allowlist.
- Before an existing canonical Draft branch can be reused, fetch and verify its
  native helper subset against the base lock identity and byte-for-byte derived
  output; remove the transient fetch credential before invoking the helper.
- Updated the security contract, direct negative tests, bilingual workflow
  security/tooling documentation, and this paired record.

No Parent, MRTS, release, settings, secret, dependency, or default-branch
change is included.

## Security impact

The consolidation preserves the trusted-default checkout, top-level
`contents: read`, separate read-only candidate job, repository-limited App
token, fixed Draft PR, and no-force/no-merge posture. The new snapshot accepts
only owned non-symlink `RUNNER_TEMP` directories. The helper remains bounded
to explicit lock/workflow/documentation paths and never executes a downloaded
asset. Reusable canonical branches must match both the reviewed scope and the
native base-derived content; the App token is unset before the helper runs.

## Documentation and runtime evidence

The bilingual workflow-security and CI-tooling documents and this paired Change
Record describe the single-publisher boundary and the retained native controls.
Local tests provide source-level evidence for those contracts.

## Checks not run

No hosted execution of the new source was run: before an authorized merge, the
trusted workflow deliberately checks out `master`, so a dispatch would execute
the old default-branch source rather than this PR source.

API, artifact, and publisher-environment evidence. No default-branch dispatch
